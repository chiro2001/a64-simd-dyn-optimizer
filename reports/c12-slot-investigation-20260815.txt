# costC1C2Flag 槽位替换排查（2026-08-15）

## 现象

920B 真机（build/x265-8-gcc，单核单线程、30 帧 1080p）：

| 状态 | md5 | bitrate / QP |
| --- | --- | --- |
| 干净基线（确定性，3 次一致） | ee5db7384df974ba25e4f1df8178dcb6 | 7981.54 kb/s / 33.77 |
| patch costC1C2Flag = NEON run-cache 候选 | 22c4b76a6cefee02923d40b26f644def | 7974.26 kb/s / 33.78 |
| patch costC1C2Flag = 与 C 参考逐字相同的标量副本 | 22c4b76a6cefee02923d40b26f644def | 7974.26 kb/s / 33.78 |
| patch costCoeffRemain（仅 remain） | ee5db7384df974ba25e4f1df8178dcb6 | 7981.54 kb/s / 33.77 |

## 已排除

- 候选逻辑错误：NEON 候选 200k 全值域差分 0 失配；真实路径诊断（候选
  与参考逐调用对比 sum 与 64 字节 ctx）未触发差异。
- 槽位偏移错误：offsetof 验证 costC1C2Flag=7072、costCoeffRemain=7064，
  patch 汇编写入偏移一致。
- 链接候选对象本身改变输出：不 patch 仅链接对象输出仍为基线。
- 编码非确定性：基线 3 次编码 md5 相同。

## 结论

把 costC1C2Flag 槽位替换为**任意**等价实现都会改变编码输出，与实现逻辑
无关。原因未明（可能该槽位存在未记录的副作用/调用时机依赖）。该 kernel
暂不用于 E2E 注入；costCoeffRemain 确认可注入。

## round-0024 更新：谜底已定位

根因不是“槽位替换机制”，而是候选 NEON 路径的掩码越界：

- 候选 `vld1q_u16(absCoeff)` 读满 8 lane，但只有前 `n` 个属于当前
  chunk；真实路径中 `n` 之后是后续非零系数的绝对值（常见 >1），旧代码
  的 `first = ctz(m1)` 会把这些垃圾位当成“第一个大系数”，污染上下文
  更新；
- 旧差分语料全值域随机，`absCoeff≤1` 概率极低，从未覆盖 `first ≥ n`
  场景，所以 200k 差分也通过；
- 修复：`m1/m2 &= (1<<n)-1`（按 n 截断），并把差分语料改为“前 n 个偏
  小值 + n 后全范围随机”——**修复后注入码流与基线完全一致
  （ee5db7…）**，加强语料 200k 差分 0 失配。

### 真实 n 分布下的性能问题（待续）

修复后 E2E 仍慢 ~0.9%（8.25s vs 基线 8.18s）。920B 微基准按 n 细分：

| n | neon/cand 比率 |
| --- | ---: |
| 1 | 0.84（候选慢 1.19×） |
| 2 | 0.78 |
| 3 | 0.95 |
| 4 | 0.96 |
| 5 | 1.32 |
| 6 | 1.53 |
| 7 | 1.81 |
| 8 | 2.13 |

run-cache 只在 n≥5 快；已加 n≤4 标量分流，但 E2E 仍慢，说明真实调用
n 分布偏小或存在固定调用开销。下一步：抓真实 n 直方图，按分布设计
（或对小 n 用更薄的标量路径）。

## 附注

排查过程中发现：云端多次实验会污染 build.ninja 链接行与第三方源码状态，
导致误判（早前“remain 改变码流”即由此而来）。每次实验前必须
`git -C third_party/x265 checkout -- .` + 清空链接行 + 重编
primitives/entropy/dct 三个对象，并以 3 次确定性编码为基线。
