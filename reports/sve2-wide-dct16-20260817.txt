## pure_sve2 mode: VALIDATED bit-exact vs op895 (2026-08-17)

Uses validated pure SVE2 cross-row butterfly:
- Per-row: svrev_s16 → svunpklo_s32 → svrev_s32 → svadd/svsub (1 permute/row)
- Cross-row: svzip1_s64 → svext_s32(4) → revw_d32 → svadd/svsub (3 permutes/pair)
- Reduction: addp_s32 + svtbl swap {0,2,1,3} at each level

Key discovery: SVE `addp` interleaves pairs from src1/src2, while NEON
`vpaddq_s32` takes ALL pairs from src1 first. This requires `svtbl` swap
at each addp level to match vpaddq ordering.

Also: SVE `addp` instruction requires zd==zn (RMW constraint), creating
serial dependency chains that inflate critical path latency (277 vs 55
for neon_bridge).

## Key Findings

### 1. neon_bridge mode VALIDATED (bit-exact vs op895)

The neon_bridge mode reproduces op895's algorithm using the same NEON
intrinsics for the even-k section (vaddl_s16, vrev64q_s32, vpaddq_s32,
vmulq_s32, vrshrn_n_s32) and the same SVE2 for odd-k (svdot_s64).

QEMU validation: 200 iterations × 6 modes, 0 mismatch vs op895.

Static counts (-O3 -march=armv8-a+sve2):
- vector_fused_uop: 950 (vs op895 952)
- critical_path_latency: 55 (vs op895 52)
- permute_on_critical: 3 (vs op895 5)
- permute_depth_ratio: 12.0% (vs op895 18.5%)
- spill_reload: 27 (vs op895 20)

### 2. SVE2 width-native butterfly FUNDAMENTAL BUG

The addp/uzp modes (pure SVE2 even-k) produce WRONG results because
the SVE2 width-native butterfly uses svsplice+svtbl which creates an
INTRA-row reversal (reversing within each row's 4 elements), while
op895 uses zip1_s64+rev64+zip2_s64 which creates a CROSS-row butterfly
(interleaving elements from two different rows).

These are mathematically different operations:
- Intra-row: EEE[i] = EE[i][0]+EE[i][3], EE[i][1]+EE[i][2], ...
- Cross-row: EEE[0] = EE[0][0]+EE[1][3], EE[0][1]+EE[1][2], ...

The cross-row butterfly cannot be replicated with simple svsplice+svtbl
at VL=256. It requires either:
a) NEON bridge (zip1q_s64/rev64q_s32/zip2q_s64) — used by op895
b) SVE2 svzip1_s64/svzip2_s64 + a per-64-bit reversal (revw_d64)
c) A completely different algorithm that avoids the cross-row butterfly

### 3. addp_s32 creates LONGER critical path

Using `addp_s32` (inline asm `addp r, r, b` with "+w" constraint)
instead of `uzp1+uzp2+add` creates a read-modify-write dependency that
extends the critical path:
- addp mode: cp_lat=358, cp_len=145, permute_ratio=41.4%
- uzp mode: cp_lat=128, cp_len=98, permute_ratio=53.1%

The addp instruction IS in MNEMONIC_LATENCY (latency=3) but the "+w"
constraint creates a serial chain that makes the critical path longer.

### 4. neon_bridge permute_depth_ratio improvement

The neon_bridge mode achieves permute_depth_ratio=12.0% (vs op895's
18.5%). This is likely due to the emitter's code ordering affecting
compiler register allocation and scheduling, not a fundamental
algorithmic improvement. The difference is small (3 vs 5 permutes
on critical path) and may not translate to real-world improvement.
