# 指令融合分析（Instruction Fusion Analysis）需求梳理 v0.1

状态：**待审核**。本文档只做需求梳理，不包含实现；审核通过后作为
P0 需求冻结，进入 `optimizer/analysis/fusion` 与 `tools/fusion_analysis.py`
的 v0.1 实现。

## 1. 背景与目标修订

### 1.1 目标 CPU

- 主目标：鲲鹏 N+2 代，支持 **SVE2/SVE256**；
- 后续型号：SVE 支持 **4×256-bit** 执行 pipe，NEON 仅 **4×128-bit**；
- 当前 CPU 处于需求分析与负载导入阶段，无实机 profile，也没有可确认的
  微架构融合表。

### 1.2 优化口径修订

此前项目文档（`docs/README.md`、`docs/01-project-charter.md`）把方向目标
写为“同一机器、同一 ISA 档位下 +30%”。按本轮需求修订为：

- **相同 ISA/算力口径**：+30%（保留原口径，用于 NEON→NEON 或同档位优化）；
- **跨 ISA 宽度迁移口径（新）**：在鲲鹏 N+2 上把 kernel 从 NEON 迁移到
  SVE256，且执行 pipe 数量相同（NEON 4×128 → SVE 4×256），目标为
  **+130%**（即 2.3×）。

### 1.3 为什么需要指令融合分析

按用户给定的 pipe 假设，SVE256 相对 NEON128 的峰值数据宽度为 2×（+100%），
要达成 +130%（2.3×）需要额外约 15% 的收益。这些收益只能来自：

- 动态指令数下降（加载合并、重排消除、归约融合，现有工具已覆盖一部分）；
- **执行级指令融合**（两条 SIMD 指令合并为一条融合指令/uop，节省发射与
  执行 pipe 占用）；
- 关键路径/调度优化。

因此分析套件需要新增“指令融合分析”能力，把可融合序列识别、端口预算、
依赖检查和预期收益纳入候选筛选，并为后续实机校准提供预测-实测闭环。

> 备注：2× 宽度 + 15% 是**基于用户给定 pipe 假设的推断**，不是实测结论；
> 最终以鲲鹏 N+2 target profile 和 workload 冻结结果为准。

## 2. 术语与融合分层

为避免把三类不同事物混在一起，本需求先明确分层：

1. **微架构级融合（macro-op / fusion）**：执行引擎把两条（或更多）架构
   指令合并为一条融合 uop 处理，节省发射槽与执行 pipe 占用。ISA 不变，
   架构语义不变。这是本需求的**主分析对象**。
2. **ISA 级合并**：用一条真实 ISA 指令替换两条（例如 `add + shift` →
   移位寄存器 ADD，或本项目已完成的 `TBL2+索引装载 → TRN`）。这类变化
   会改变动态指令数，属于现有指令选择/搜索工具的能力，不是融合分析。
3. **SVE2 复合/特殊形态**：如 `MOVPRFX + destructive op` 的组合语义、
   SVE2p1 的 128-bit 段级操作。它们可作为融合候选的特殊来源，但语义
   验证必须单独处理。

融合分析 v0.1 只做第 1 层（预测）和第 3 层（候选标注），不生成第 2 层
以外的 ISA 变换。

## 3. 融合条件（用户给定，逐条细化）

### C1：同类 SIMD 指令

- 两条源指令必须都是 NEON（ASIMD）、SVE、SVE2 向量指令；
- 谓词指令（`whilelt`、谓词逻辑）单独归类，默认不参与融合；
- 标量 GPR、内存 load/store、分支、system 指令默认排除（v0.1）。

### C2：融合后视为一条指令执行

- 分析器以“融合后发射数 2→1、执行 pipe 占用按 1 个 slot 计”建模；
- 这是**预测模型**：QEMU 不模拟微架构融合，真实融合行为由目标 CPU
  微架构决定，必须在实机 PMU 校准；
- 每个候选必须带 `needs_hw_verify: true` 状态，禁止把预测当作已实现收益。

### C3：读/写寄存器端口约束

融合后指令必须满足：

- **读寄存器端口 ≤ 3**；
- **写寄存器端口 == 1**。

端口计数规则（v0.1 提案，可配置）：

| 操作数类型 | 计数规则 |
| --- | --- |
| 向量源寄存器（Z/V） | 每个**不同**源寄存器计 1 读口；同一寄存器多次出现仍计 1 |
| 谓词寄存器（P） | 计 1 读口（默认计，可配置为 0） |
| 标量 GPR 源 | 计 1 读口；v0.1 默认**不允许**含标量源的指令对参与 |
| 立即数 / 索引 / 移位量 / 位宽说明符 | 不计 |
| 内存操作数 | v0.1 不允许参与融合 |
| 目的寄存器 | 唯一向量寄存器，计 1 写口 |

示例（用户给定）：

- `add z0, z1, z2; fcvt z0, z0`：读 2（z1,z2）、写 1（z0），可融合候选
  `add_fcvt z0, z1, z2`；
- `add z0, z1, z2; tbl z0, z0, z4`：读 3（z1,z2,z4）、写 1（z0），可融合
  候选。

端口模型由 `TargetProfile` 参数化（例如 3R1W / 4R2W），默认 3R1W。

### C4：数据依赖与语义条件

除端口预算外，还必须满足（任一不满足即拒绝）：

1. **严格相邻**（v0.1 默认窗口 N=1）：两条指令在目标执行序列中直接相邻，
   中间没有其它指令；N 可配置以允许“中间仅无副作用 move/reinterpret”
   的情况。
2. **中间结果不可观察**：第一条指令的目的寄存器只被第二条指令读取，
   不被序列中其它指令使用；否则融合会改变可观察语义（融合后中间结果
   可能不再单独存在）。
3. **目的链接**：第二条指令的目的与第一条目的相同（dest chaining），
   或第二条只读第一条结果并写一个新目的（保守：v0.1 只接受前者）。
4. **谓词一致**：若两条都带谓词，谓词寄存器必须相同；否则拒绝。
5. **类型/位宽兼容**：第二条的源类型与第一条结果类型一致，或仅相差
   零成本位视图（u16/u32/u64 reinterpret，现有 codegen 已按零成本处理）。
6. **无副作用/边界**：两条指令之间不得跨 load/store、分支、异常边界、
   标志写（v0.1 保守排除）。

### C5：可扩展性

- 融合对不限于 2 条：端口预算按整体计算后可扩展 3 条链式融合；
- 融合对表可配置：真实 CPU 的融合能力表由 `TargetProfile.fusion_table`
   提供；未提供时分析器只按 C1–C4 枚举“候选”，并全部标记
   `needs_hw_verify`。

## 4. 分析能力需求

### 4.1 输入

- 目标 kernel 的最终汇编（objdump / llvm-objdump，生产 flags）或
  MachineIR 指令序列；
- `TargetProfile`：ISA 档位、VL、端口模型、融合对表（可选）、窗口大小；
- 可选：关键路径/依赖图（来自 MachineIR），用于评估融合对 latency 的影响。

### 4.2 输出

每 kernel 一份 JSON 报告：

```yaml
kernel: dynopt_sa8d_16x16_neon_sve2
profile: kunpeng-n2-sve256-v0
status: prediction          # 融合是预测，不是实测
pairs:
  - index: 42
    insn1: {mnemonic: add, operands: "z0.h, z1.h, z2.h"}
    insn2: {mnemonic: fcvt, operands: "z0.h, z0.h"}
    read_ports: 2
    write_ports: 1
    dependency_ok: true
    predicate_ok: true
    type_ok: true
    savings: {issue_slots: 1, pipe_slots: 1, dynamic_insns: 1}
    needs_hw_verify: true
summary:
  total_pairs: N
  predicted_dynamic_insns_saved: N
  predicted_issue_slots_saved: N
  critical_path_impact: neutral|worse|unknown
```

报告必须同时给出：

- 端口预算与依赖检查的逐项通过/拒绝原因；
- 融合对**不自动缩短关键路径**的提示：`add;fcvt` 仍是一条串行依赖链，
  融合主要收益在发射/pipe 占用，不在 latency；若目标 CPU 融合后延迟等于
  两条之和，则 latency 无收益；
- `needs_hw_verify` 标记与实机 PMU 对比字段（`hw_cycles_ratio` 等，预留）。

### 4.3 与现有工具链集成

- 复用 `tools/count_asm_insns.py` 的指令分类与 `optimizer/targets/aarch64/`
  的 TargetFeatures/TargetProfile 概念；
- 新增独立模块 `optimizer/analysis/fusion.py` 与 CLI
  `tools/fusion_analysis.py`；
- 候选输出进入实验目录（建议 `experiments/m11-fusion/`），与现有
  候选漏斗并列；正确性仍由现有差分门禁负责（融合不改变 ISA 语义，
  差分验证照常覆盖）；
- 融合候选作为静态筛选信号，不自动进入 benchmark 接受路径。

### 4.4 正确性边界

- 融合分析**不生成**新的 ISA 指令，不改变 kernel 汇编；
- 对每个候选，若融合后存在理想单指令语义（如第 3 层 SVE2 复合），用
  MachineIR 语义/差分确认不影响可观察结果；
- 若融合后指令在 ISA 中不存在（如 `add_fcvt`），只做预测，不做任何
  代码生成。

## 5. 验收标准（v0.1）

1. 能对现有 SVE2 候选（`sve_roundtrip_sa8d_8x8x2raw.cpp`、
   `sve_roundtrip_sa8d_16x16.cpp`）产出融合分析报告；
2. 端口计数（3R1W）、依赖链拒绝、谓词不一致拒绝、窗口参数化均有单元
   测试；
3. 报告明确区分“候选可融合（按条件）”与“目标 CPU 支持（待验证）”，
   所有预测项带 `needs_hw_verify`；
4. 与 `count_asm_insns.py` 结果可以合并出“动态指令减少上限”的估计；
5. 同一报告可在鲲鹏 N+2 profile 未定时以默认参数运行，不因缺融合表而
   崩溃（降级为按 C1–C4 枚举）。

## 7. 开放问题（需审核确认）

1. **端口计数细则**：谓词寄存器是否计 1 读口？同寄存器多次出现是否只计 1？
   标量 GPR 源是否允许（如 `whilelt + op`）？v0.1 提案见表，请确认。
2. **窗口**：只允许严格相邻（N=1），还是允许中间只有无副作用
   move/reinterpret（N=2/3）？
3. **融合对表**：`add+fcvt`、`add+tbl` 是示例还是鲲鹏已确认的融合对？
   分析器默认“按条件枚举 + 全部标待验证”是否可接受？
4. **+130% 基线**：“相同 pipe”的精确定义与基线实现：是 x265 当前 NEON
   实现、上游 SVE2 实现，还是理想 2× 宽度模型？workload 权重何时冻结？
5. **分析对象范围**：只分析优化器生成的候选，还是也包括上游 x265
   NEON/SVE2 汇编？
6. **load/store 是否参与融合**：v0.1 建议排除（LD1+ADD 类融合需要
   内存端口模型，复杂度高），是否同意？
7. **融合结果是否驱动搜索**：v0.1 只做静态报告；是否要求后续把“可融合
   序列”作为布局搜索的收益项（例如优先生成 `add;tbl` 相邻形态）？
8. **文档口径同步**：`docs/README.md` 等处的“+30%”旧口径是否在本需求
   冻结后一并修订为“同算力 +30% / 跨 ISA 同 pipe +130%”双口径？

## 8. 风险

- **融合对未知**：若鲲鹏 N+2 实际融合支持与条件不符，预测收益会高估；
  缓解：融合表可配置、默认只报告、全部 `needs_hw_verify`。
- **端口模型假设错误**：读口计数规则与真实重命名/读口结构可能不同；
  缓解：TargetProfile 参数化，P3 实机校准。
- **融合可能恶化调度/关键路径**：融合减少发射但不缩短依赖链，甚至增加
  pipe 竞争；缓解：报告必须输出 `critical_path_impact`，不单独以融合对数
  作为收益。
- **QEMU 无法验证融合**：正确性仍由差分保证；性能预测只能等实机。
- **目标 CPU 未定型**：所有收益数字均为参数化模型；需求冻结不代表
  profile 冻结。
